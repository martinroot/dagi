## Продолжение после восстановления SSH-доступа

1. Администратор сервера должен установить публичный ключ, соответствующий указанному отпечатку, в `authorized_keys` **выбранной учётной записи для первоначальной настройки**, либо предоставить отдельный подтверждённый SSH-способ доступа. Не пересылать приватный ключ.
2. Проверить отпечаток сервера по независимому каналу и сохранить правильную запись в `known_hosts_dagi`. Не использовать `StrictHostKeyChecking=no`.
3. Выполнить установку под административной учётной записью: создать отдельного непривилегированного пользователя `hermes`, установить Hermes официальным поддерживаемым способом, включить службу под этим пользователем и проверить её статус. Не запускать агента постоянно от `root`.
4. Ввести собственный ключ провайдера модели и токен Telegram-бота, созданный владельцем через BotFather, непосредственно в защищённые файлы на сервере. Каталог/файлы должны принадлежать `hermes`, иметь права не шире `0700`/`0600`; не передавать секреты аргументами команд, через чат, shell history или логи. Не копировать существующие локальные credentials.
5. Настроить Telegram-канал Hermes в конфигурации сервера и запустить/перезапустить службу.
6. Проверить без вывода credentials: статус службы, наличие Telegram polling/подключения и ответ бота на тестовое сообщение от разрешённого аккаунта. Зафиксировать только итоговые статусы и пути к защищённым файлам.

## Безопасная повторная проверка доступа

После установки администратором соответствующего публичного ключа проверить только известные учётные записи, например:

```sh
ssh -i /home/dagi/.ssh/id_ed25519_hermeskanban \
  -o IdentitiesOnly=yes \
  -o UserKnownHostsFile=/home/dagi/.ssh/known_hosts_dagi \
  -o StrictHostKeyChecking=yes \
  -o ConnectTimeout=8 USER@145.223.69.147 'id; hostname'
```

Заменить `USER` на согласованную учётную запись. Успешный SSH-вход — лишь предпосылка, не доказательство установки или работы Telegram-бота.
